We divide the design of the entire Buckyball repository into two parts: specific chips and the main architecture.

Why split it this way? Because design and usage patterns are coupled. Most of the repository belongs to the main architecture; under `examples/` are concrete example implementations built on different versions of the repository, some of which have been validated through tapeout. We want chip-specific design and the main architecture to be decoupled. The architecture covers many aspects: anything in the DSA design process that can be abstracted and shared is treated as mainline. Concrete examples include simulation and acceleration toolchains such as bbdev and FPGA acceleration. Building a separate toolchain for every design is not worthwhile. Buckyball establishes unified abstractions so different designs can share the same infrastructure. The compiler is an MLIR-based compiler that turns frontend code such as common PyTorch or Triton into executables. Each specific chip has its own instruction set, extended on top of the shared Buckyball base. Then there is chip RTL. For the verification framework, the architecture side builds a system-level UVM framework, and each Ball reuses that framework internally to keep Ball-level coverage complete.

## Buckyball design philosophy

Because our system architecture is unified, we have a unified methodology for testing the system. Buckyball's architecture design follows several principles so it stays general and efficient enough for many DSA scenarios. First, one important abstraction is Ball-oriented design. Second, another important abstraction is the bank: we set the granularity of memory access tracking and operations to half-bank, which is relatively coarse in typical systems. Third, we follow a little-to-big board scaling philosophy. Based on these choices we built a general framework. By default, chip design should not modify the main architecture. If the main architecture cannot meet a chip's needs, the Buckyball architecture framework should be iterated to support that capability. For main-architecture design and specific chip introductions, see [main architecture overview](main-arch/0.0.1/overview/overview.md) and [Pebble overview](chips/pebble/overview.md). To further explain how Buckyball separates architecture from design, we walk through the division of labor for specific chip design. On the compiler side, Buckyball provides an MLIR framework and buddy-LLVM maintenance. When you add a new design, choose your Balls and instructions and build your own buddy-LLVM backend dialect and passes. For tools: when you add a new Ball, or when you add a new chip. For RTL: when you add a new Ball, implement it directly under prototypes. When a chip needs a new design, refer to pebble and fork directly.
